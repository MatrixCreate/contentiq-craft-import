# Import pipeline — the life of a sync

This covers what happens to a page once its JSON has arrived in Craft: the four ways a sync can start, how they all funnel through one pipeline method, how that method decides whether it's creating or updating an entry, why it saves the way it does, how collection children (blog posts, case studies, team members) differ from ordinary pages, and the tables that remember state between runs. It assumes you've already read [integration.md](integration.md) for how the JSON gets fetched in the first place.

Verified against code 2026-09-21.

## Four entry points, one pipeline method

Every way of getting ContentiQ content into Craft ends up calling `ImportService::importPage(array $data, bool $dryRun, bool $verbose): array` (`src/services/ImportService.php:79`) once per page:

- **CLI** — `php craft contentiq-importer/import --file=export.json`. `ImportController::_runSinglePage()` (`src/console/controllers/ImportController.php:433`) calls it directly; `_runBatch()` loops it once per page in a batch file. This is a standalone implementation, deliberately untouched by the batched pipeline below — see "The job chain — phase by phase".
- **CP upload, CP Sync, and `sync/run` (CLI)** — all three now stage a `contentiq_import_runs` row and hand off to the same batched job chain (`StageRunJob` → `ImportPagesJob` → `PostPassJob` → `FinaliseRunJob`), which calls `importPage()` once per `contentiq_sync_pages` row from `ImportPagesJob::_processPage()` (`src/jobs/ImportPagesJob.php`). `CpController::actionRunImport()` (upload), `CpController::actionRunSync()` (the live-API "click Sync" path), and `SyncController::actionRun()` (`php craft contentiq-importer/sync/run`) differ only in how they obtain the payload and what `source` (`upload`/`api`/`cli`) they stamp on the run — see "The job chain — phase by phase" below.
- **Sidebar widget single-page sync** — `CpController::actionWidgetSync()` (`src/controllers/CpController.php:1182`), one entry at a time from the entry edit screen, still synchronous (no queue job) — see [cp-and-widget.md](cp-and-widget.md).

All of the above also share one entry point for what happens after their page loop finishes, `ImportService::runPostPasses()` (`src/services/ImportService.php:624`) — see "Pass 3 — link sweep" and "Pass 4 — legacy-URL redirects" below for the full contracts. It runs PASS 2 (deferred card references, `resolveCardReferences()`), PASS 3 (the link sweep, `LinkSweepService::sweep()`), and PASS 4 (legacy-URL redirects, `RedirectService::sweep()`) together, once every page in the run has been imported and before ack/auto-lock. Callers should reach all three passes through `runPostPasses()`, not call `resolveCardReferences()` directly — doing so silently skips PASS 3 and PASS 4. Three call sites reach it: `PostPassJob` (`src/jobs/PostPassJob.php`, batched — covers CP upload, CP Sync, and `sync/run` alike, since all three share one pipeline), `CpController::actionWidgetSync()` (`src/controllers/CpController.php`, the sidebar's single-page sync), and the CLI's `ImportController::actionImport()` and its `_runBatch()` (`src/console/controllers/ImportController.php`, single-page and batch-file imports, unaffected by the pipeline). See "cards" in [block-mapping.md](block-mapping.md) for what PASS 2 resolves; this doc only covers where these passes sit in the sequence.

Because every entry point reaches the same `importPage()`, a bug fix or behaviour change made in `ImportService` applies uniformly — there's no separate "CLI import logic" to keep in sync with "widget import logic." Each entry point differs only in: how it gets the JSON, whether it enforces the lock check before calling in (CLI and the widget check locks themselves before calling `importPage()`; `ImportPagesJob` does too, per row), and what it does with the result afterward (report rendering, audit-trail row, ack call).

## The job chain — phase by phase

Where `SyncJob::execute()` (removed after one release as a compatibility shim — see below) used to do everything in one unbounded `execute()`, a pipeline run (`source` `api`/`upload`/`cli` — the widget stays a single synchronous `importPage()` call, untouched) now advances through four small queue jobs, each bounded by Craft's own `BaseBatchedJob` time/memory projection instead of one long-running process. A `contentiq_import_runs` row's `phase` column (`staging`|`importing`|`postpass`|`finalising`|`done`|`failed`) tracks where a run is; `contentiq_sync_pages` — one row per page in the run, see "Tracking tables" below — is what lets every job resume mid-run instead of re-doing everything from the top. The **run row and its `contentiq_sync_pages` rows are the only things that cross a job boundary** — a job's own payload carries nothing but its run id (plus Craft's own batch offsets); see "State that crosses job boundaries" below for what that means for state that used to live in one PHP process.

1. **`staging`** — `StageRunJob::execute()` (`src/jobs/StageRunJob.php`). Applies this run's lock/unlock selection and globals consent (`SyncLockService::applyLockState()`/`setGlobalsLock()`) — at job execution, never at the controller request, same rule as before (a worker that never picks up the job leaks nothing; IDs are sanitised first — cast to positive int, deduped, filtered to real Craft entries — since they arrive from a POST body). `_applyLockState()`'s unlock branch is an upsert, not an UPDATE-only — an entry with no `contentiq_entry_syncs` row yet (the Craft homepage Single is the standing example: it pre-exists so `findExistingEntry()` matches it, but its row is only ever created by the `finalising`/`lock` step below) gets a fresh `locked => false` row inserted rather than a no-op UPDATE that the missing-row-means-locked check would then immediately re-skip. Then obtains the export payload — `ContentIQApiService::fetchExport()` for `source=api`, or the file a controller/console command already saved to disk for `source=upload`/`cli` — validates the envelope (a failed fetch or a non-array decoded body fails the run immediately), and hands the decoded array to `SyncPlanner::plan()` (`src/services/SyncPlanner.php` — pure, no `Craft::` calls, unit-tested in `tests/run-transforms.php`), which turns it into one planned row per page (position, slug, parent_slug, depth, content_type, `duplicate_slug`, the page's own payload) plus a synthetic `skipped_malformed` row for anything unimportable. `SyncRunService::stageRun()` persists that plan in chunks of 100 — the whole decoded export is held in memory for exactly this one pass, never longer (the spec's phase-1 memory ceiling). Advances to `importing` and pushes `ImportPagesJob`.
2. **`importing`** — `ImportPagesJob` (`src/jobs/ImportPagesJob.php`), a `craft\queue\BaseBatchedJob` (20 pages/batch by default, configurable — see [integration.md](integration.md#config-surface)) over the run's `contentiq_sync_pages` rows in export-position order. Per `pending` row (`_processPage()`): the lock check via `findExistingEntry()` and the assets-only path for a locked entry, the deselected-"New" skip, then `importPage()` and — for ordinary Structure pages, never collection children — `positionInStructure()`. This is Pass 1 below, unchanged in *what* it does; what changed is that it now runs one row at a time, persisting the row's status/`entry_id`/full `importPage()` result as it goes (see "Per-page results are the full `importPage()` row" below) instead of looping the whole export in one PHP process. Advances to `postpass` and pushes `PostPassJob` once every row has a terminal status.
3. **`postpass`** — `PostPassJob` (`src/jobs/PostPassJob.php`), batched (50 rows/batch by default) over rows with `status=imported`. Calls `ImportService::runPostPasses()` per batch — Pass 2 (deferred card references), Pass 3 (the link sweep), Pass 4 (legacy-URL redirects), exactly as before; see those sections below for what each pass does, which is unchanged. Stamps `postpass_done` per row once its batch has run. Advances to `finalising` (`step=ack`) and pushes `FinaliseRunJob`.
4. **`finalising`** — `FinaliseRunJob` (`src/jobs/FinaliseRunJob.php`), a single job that steps through four sub-steps recorded in `run.step`, each resumable independently because each stamps its own progress per row/chunk:
   - **`ack`** — see [integration.md](integration.md#read-only-export--explicit-ack-contract). `POST /api/v1/pages/ack`, chunked at 500 (the API's own `max:500`), stamping `acked_at` per successful chunk so a resumed ack step only resends the remainder. Skipped entirely for `source=upload`/`cli` — no live ContentiQ page ids to acknowledge against, same as before.
   - **`globals`** — the drift check (always runs, read-only) plus the consented globals import, verbatim from the pre-pipeline behaviour. Only runs when the export carried a `globals` key **and** the globals-consent row is unlocked for this run. See [globals.md](globals.md).
   - **`lock`** — every successfully-synced entry (not skipped-locked) gets `contentiq_entry_syncs.locked` set back to `true`, plus `synced_at`, `sort_order`, and the aggregated block notes — stamping `locked_at` per row as it goes. This is what makes a sync self-limiting: once imported, a page won't be touched again until a human explicitly unlocks it for the next run. Unlike `ack`, this step is **not** skipped for `source=upload` — a CP-uploaded JSON file now gets the same auto-lock/`sort_order` persistence a live sync always got (see "Persistence" under "Hierarchy" below for what that changes for the upload path specifically).
   - **`report`** — assembles the legacy `{pages, globals, ackWarning}` result JSON from the run's rows (kept for backward compatibility with the report templates — new report code reads the rows directly, see [cp-and-widget.md](cp-and-widget.md)) and sets `phase=done`.

A `Throwable` anywhere in the chain fails the run (`phase=failed`), relocks globals, and records the phase/step it died in (`run.state.failedPhase`/`failedStep`) so a resume knows where to restart — see "Resuming a run" below.

### State that crosses job boundaries

A job's own payload is never more than its run id (plus the batch offsets `BaseBatchedJob` itself adds) — every `execute()` starts by loading the run (and, for a batched job, its page rows) fresh off the database. Two pieces of state that used to live in local PHP variables for the whole run now have to be explicitly rebuilt every batch (`ImportPagesJob::beforeBatch()`/`afterBatch()`):

- **The "first global CTA block wins" flag** — `ImportService::$_globalCtaResolvedThisRun`, previously reset once per run by `beginRun()`. Every batch now calls `beginRun()` (resets it) immediately followed by `ImportService::restoreRunState($run->state)` (restores this run's own persisted value) — `beginRun()` must run first, or it would wipe out what `restoreRunState()` just set. `afterBatch()` writes the flag back out via `ImportService::exportRunState()` into `run.state`, so the next batch — a different PHP process, under a real queue worker — picks it up. Missing this is what would reintroduce "last page wins" bugs across batches.
- **The slug → entry ID map** — rebuilt every batch from `contentiq_sync_pages` (`SyncRunService::slugToEntryIdMap()`, `status=imported` rows) rather than accumulated in a PHP array across the whole run. Parent resolution falls back to a live Craft query when a parent isn't in this map (an earlier-batch import, or a re-sync), same as before.

Everything else the old single-process run kept in local variables — duplicate-slug detection, the accumulated card-ref map, the page-results array, the ack set — is now either computed once at staging (`duplicate_slug`, over the whole plan) or read back from `contentiq_sync_pages` rows on demand, never carried in a job's own state.

### Per-page results are the full `importPage()` row

`SyncRunService::markPage()` persists exactly what `importPage()` (or the locked/deselected skip branches in `ImportPagesJob`, which build the same shape) returned — never a hand-built subset. This is the same rule `runPostPasses()` has always enforced (AGENTS.md's hard limit): `PostPassJob` and `FinaliseRunJob`'s `report` step both read `blockNotes`/`sortOrder`/`contentiqPageId`/`cardRefs`/`legacyUrl` straight off `contentiq_sync_pages.result`, so a caller that wrote a narrower row would silently break both.

### Per-item idempotency

Every job checks `run.phase` before doing anything — a mismatch (already advanced, or failed by the staleness fallback) means the job returns without touching anything, so a double-push or a stale retry is harmless. Every batched job's `processItem()` additionally checks the row's own state before doing anything: `ImportPagesJob` only imports a row whose `status` is still `pending`; `PostPassJob` only post-passes a row whose `postpass_done` is still `0`. A killed batch therefore resumes at exactly the rows a prior execution didn't finish — it never re-imports or re-sweeps a row that already succeeded.

### Resuming a run

A `failed` run records which phase (and, inside `finalising`, which step) it died in — `run.state.failedPhase`/`failedStep`, written by `SyncRunService::fail()` from the row's state immediately before it's overwritten to `phase=failed`. `php craft contentiq-importer/sync/resume <runId>` (`SyncController::actionResume()`) and the CP Sync screen's Resume button (`CpController::actionResumeRun()`, wired up in `sync.twig`) do the same thing: refuse if something is already queued for the run (`SyncRunService::hasQueuedJob()`), then re-push the job class matching the recorded phase/step. Because every job's own idempotency rule (above) means it only touches unfinished rows, a resumed run never re-imports or re-acks anything a prior execution already completed.

### Staleness

A non-terminal run's `heartbeat` column — touched by every job execution and every processed item — going stale (older than `queue.staleAfter`, default 600s — see [integration.md](integration.md#config-surface)) **and** nothing left queued for the run's `queueJobId` in Craft's own `{{%queue}}` table (`SyncRunService::hasQueuedJob()`) is what tells the CP status poller (`CpController::actionSyncStatus()`) and the "start a new sync" guard (`actionRunSync()`) that the worker died without any failure handler running. Either path fails the run and relocks globals, same as any other failure, then offers Resume.

**`SyncJob` is a one-release compatibility shim, not a live entry point.** Craft unserialises a queued job by class name, so any `SyncJob` payload still sitting in the `{{%queue}}` table at the moment this release deploys needs the class to still exist — `src/jobs/SyncJob.php`'s `execute()` no longer runs a sync itself, it converts the run row it was pushed for into a `phase=staging` pipeline run and hands off to `StageRunJob`. It's scheduled for removal in the release after this one, once no pre-deploy payload can plausibly still be queued.

## Pass 3 — link sweep

Runs immediately after PASS 2, inside the same `ImportService::runPostPasses()` call (`src/services/ImportService.php:624`) — the single entry point every one of the three call sites above uses for both deferred passes; calling `resolveCardReferences()` directly skips PASS 3 entirely. Implemented in `LinkSweepService::sweep()` (`src/services/LinkSweepService.php`); the pure string/array half it's built on is `LinkRewriter` (`src/helpers/LinkRewriter.php`).

**Why.** ContentiQ exports internal links as root-relative paths only — `/`, `/parent/child`, `/{url_prefix}/{slug}` — never an absolute URL. Rich-text link marks land as `<a href>` inside CKEditor HTML; hero/CTA/action buttons and detected-mode card buttons (see [block-mapping.md](block-mapping.md#cards-block)) land as Hyper `Url` links. Pages import one at a time, so a link's target page may not have a Craft entry yet when the page holding the link is written. The sweep runs once every page in the run has an entry id, upgrading every root-relative link written this run into a live reference — one that survives the target moving, being renamed, or losing its ContentiQ-assigned slug.

**Scope — written-this-run only.** `runPostPasses()` reduces `$pageResults` to the elements genuinely written this run via `ImportService::_writtenPages()` — the same predicate `FinaliseRunJob`'s `ack` step (`SyncRunService::pagesToAck()`) uses (`success`, not `skippedLocked`/`skippedDeselected`/`skipped`, a real `entryId`, a `contentiqPageId`) — plus the page-scoped CTA entries recorded in `contentiq_cta_syncs` for those pages. `LinkSweepService::sweep()` re-checks `contentiq_entry_syncs.locked` defensively before touching any element, so a page that changed lock state between pass 1 and the sweep is still skipped. A locked page is never touched by the sweep — this doesn't widen the lock rules in "Lock semantics" below at all, it just means a locked page (the standing example: the Homepage, synced first and then locked before every other page that links to it gets written) only gets live links once an editor unlocks it and it re-syncs.

**Resolution.** `Craft::$app->getElements()->getElementByUri($uri, $primarySiteId, false)`, where `$uri` is the href's path with its leading `/` stripped (`''` resolves the homepage).

**Rewrites.**
- CKEditor `href` → a Craft reference tag: `{entry:ID@SITEID:url||/original-path}`. This is the same idiom `craft\htmlfield\HtmlField::serializeValue()` already applies automatically for an absolute base-URL href — it just never fires for a root-relative one, which is every href ContentiQ exports. The `||` fallback text means a target deleted after the rewrite degrades to today's plain URL rather than a broken tag.
- Hyper `Url` link → Hyper `Entry` link: `linkValue` becomes the entry id, `linkSiteId` is set, and every other key (`linkText`, `classes`, `newWindow`, …) carries over unchanged, in its original order. The Entry link-type handle is discovered at runtime from the target field's own enabled link types — a field with no Entry link type enabled is skipped silently (a target-project config gap, not something worth a page warning).

**Field walk.** Generic over the owner entry's field layout: `HtmlField` (CKEditor), Hyper, `Matrix` (recursed into every nested block), `ContentBlock` (recursed the same way, so a hero's Hyper link is covered) — effective field handles are resolved per entry type via layout overrides, same as the rest of this plugin. A nested Matrix/ContentBlock element is saved directly when one of its own fields changed; the owner entry is only re-saved when one of its own top-level fields changed. Every save is `saveElement($el, false)` — the same no-drafts, skip-validation rule as everywhere else in this plugin (see AGENTS.md's "No drafts, ever").

**Skipped silently — nothing to upgrade, nothing to warn about:**
- Anchors (`#top`), `//host` protocol-relative hrefs, absolute URLs, `mailto:`/`tel:`.
- A href/link already a reference tag (`{entry:…`).
- Hyper's own inert placeholder — a bare `https://` (see `LinkHelper::hyperInertUrl()`).
- A Hyper link whose value carries a query string or fragment (`?utm=1`, `#staff`).

**Warned — surfaced on the owner page's result row, same `warnings[]` every other pipeline step writes to:**
- `Link '/x' did not resolve to an entry — left as a URL.` (CKEditor hrefs)
- `Button link '/x' did not resolve to an entry — left as a URL.` (Hyper links)

A root-relative path that never resolves is also how a ContentiQ `url_prefix` vs. Craft section `uriFormat` mismatch surfaces — it's a discipline problem for the target project's config, not something the sweep tries to correct itself; see [integration.md](integration.md) for the config surface.

**Idempotent and dry-run-safe.** Re-sweeping an already-upgraded link is a no-op (the "already a reference tag" skip above). `LinkSweepService::sweep()` honours `dryRun: true` (resolve and warn, skip the save — the same shape `importPage()`'s own dry run uses), but no entry point currently exercises it: a CLI `--dry-run` writes no entries in pass 1, so there is nothing for the post-passes to walk and `ImportController` skips `runPostPasses()` entirely on a dry run (see "Result shape and dry-run" below).

**Test coverage.** The pure half — `LinkRewriter::rewriteHtml()`/`upgradeHyperLink()`/`isRootRelativeHref()`/`hyperLinkPath()` — is covered by `tests/run-transforms.php` via an injected `$resolve` callable, no Craft dependency. `LinkSweepService` itself (the field-layout walk, `getElementByUri()`, the lock re-check, the actual saves) has no automated coverage — the same gap `preserveBlockIdentity` has, for the same reason (no live Craft test harness in this repo) — it's live-validated only, via the checklist below.

### Live-validation checklist

Run on a real Craft instance before trusting the sweep in production — none of `LinkSweepService` itself is integration-tested:

- A multi-page batch with the Homepage first: a page later in the batch that links to the Homepage gets a live entry link in the CP once the whole batch finishes — confirmed by moving the Homepage afterward and watching the link follow.
- A hero button and a CTA-section button both flip from Url to Entry link type in the CP after a sync.
- A `detected`-mode card with a button gets both `cardLink` (now an Entry link) and `showActionButton` correctly set.
- A locked page is untouched by the sweep — no field changed, `dateUpdated` unchanged.
- Re-syncing an already-swept page produces no diff (idempotent).
- The CLI's `--dry-run` writes nothing and runs no post-passes (nothing was written to sweep); a real CLI import then reports unresolved-link warnings in the per-page output.
- A page whose ContentiQ `url_prefix` doesn't match the Craft section's `uriFormat` produces an "unresolved" warning rather than a silently dead link.
- A hero `ContentBlock` save (the Entry-link upgrade landing inside `hero.fields`) leaves every sibling hero field untouched — the same read-modify-write guarantee `_buildFooterGlobalCtaField()` relies on.
- Timing on a ~100-page batch — the sweep adds one extra field-layout walk (plus a resolve query per candidate link) on top of passes 1 and 2; confirm it doesn't meaningfully change a full-project sync's wall time.

## Pass 4 — legacy-URL redirects

Runs immediately after PASS 3, inside the same `ImportService::runPostPasses()` call — `RedirectService::sweep()` (`src/services/RedirectService.php`). Same written-this-run scope as PASS 3 (`ImportService::_writtenPages()`, extended to also carry each written entry's `legacyUrl`): never a locked/skipped/deselected page, never a page from an earlier run.

**Why.** A scraped/exported page usually carries `document.legacy_url` — the page's URL on the site being replaced. Once that page has a live Craft URI, a Retour static redirect (`redirectMatchType: 'exactmatch'`, `redirectSrcMatch: 'pathonly'`) sends the old URL straight to it, so retiring the old site doesn't 404 every inbound link/bookmark/search result.

**Guards, in order** (see `RedirectService::sweep()`'s docblock for the full rationale): `redirects.enabled` config (default `true`); at least one written page actually carries a non-empty `legacyUrl` (a project with no legacy URL data never even reaches the Retour check below); Retour installed AND enabled (`Craft::$app->getPlugins()->isPluginEnabled('retour')` + `class_exists(\nystudio107\retour\Retour::class)`) — missing Retour is ONE run-level warning attached to the first such page, not one per page, since `nystudio107/craft-retour` is never a composer dependency of this plugin (same reasoning as Hyper/SEOmatic — see AGENTS.md).

**Per page.** `legacy_url` is normalised to a root-relative canonical path (`RedirectService::legacyUrlToPath()` — scheme/host/query/fragment dropped); the destination is the entry's own `uri` after save, converted by `RedirectService::entryUriToPath()` (`/` for the homepage's `__home__`). **The destination is canonicalised to Craft's own trailing-slash URL form** (`/about-us/`, not `/about-us`) — every target site runs `addTrailingSlashesToUrls: true`. **Exception:** a "file-like" last path segment (contains a `.`, e.g. `/roofing.html`, `/index.php`) never gets a trailing slash appended — a request for `roofing.html/` never happens. A page whose normalised source path already equals its destination is skipped silently, ALL source variants included — the common case, since scrapers typically fill `legacy_url` from the page's own current URL. A source URL that carried a query string gets a once-per-page warning noting it was dropped. `saveRedirect()`'s own (`redirectSrcUrlParsed`, `siteId`) upsert makes re-syncing idempotent — re-running never creates a duplicate redirect.

**Two source rows, one destination — Ben's ruling.** Retour matches `redirectSrcMatch: 'pathonly'`/`redirectMatchType: 'exactmatch'` against the raw request URI literally, with no slash normalisation of its own — and Craft does NOT canonicalise a slash-less inbound request (`/old-kitchens`) to the trailing-slash form (`/old-kitchens/`) before routing reaches Retour's 404 handler. A single trailing-slash-only redirect therefore silently misses any inbound link/bookmark that omits the slash. `RedirectService::sourceVariants($canonicalPath)` (pure, tested in `tests/run-transforms.php`) expands the canonical path from `legacyUrlToPath()` into the distinct `redirectSrcUrl` values actually saved: both `/old-kitchens/` and `/old-kitchens` for an ordinary path (slash form first), just `/` for the root, just `/roofing.html` for a file-like path (no trailing slash by construction — there's nothing to strip). `sweep()` loops these variants and calls `saveRedirect()` once per variant, with identical config apart from `redirectSrcUrl` — a failure on one variant warns for that variant only and the loop continues to the next. The destination stays a single trailing-slash-form value regardless — it's Craft's own canonical URL, not raw request input, so there's no slash ambiguity to cover on that side. The chain check (`_existingRedirectDestination()`, below) runs once per page, not once per variant — it's about the shared destination.

**Missing URI guard.** By the time `sweep()` runs, `positionInStructure()` has already called `ImportService::refreshUri($entry)` right after moving the entry (see "Hierarchy" above), so `$entry->uri` is normally populated. As a belt-and-braces check — in case a future caller of `runPostPasses()` skips that inline refresh — `sweep()` itself checks `$entry->uri` for each candidate and, if it's null/empty (and the entry isn't the homepage's `__home__`), attempts one more inline `updateElementSlugAndUri($entry, true, false, false)` before giving up. If the URI is still empty after that, the page gets the warning `Entry {id} has no URI yet — legacy redirect skipped.` and is skipped — never a redirect built from a missing URI resolving to `/`, which is what happened in production before this guard existed (every legacy URL 301'd to the homepage instead of its real page).

**This pass never deletes an existing Retour redirect.** `saveRedirect()` is always called with `checkForRedirectLoop: false` — Retour's own loop prevention (`checkForRedirectLoop: true`) silently DELETES any existing redirect whose `redirectSrcUrl` equals the new redirect's `redirectDestUrl`, with no ownership check at all; a hand-made CP redirect `/promotions → /new-offers` would vanish the moment this pass created `/promos → /promotions` for an unrelated page. Instead, before saving, `RedirectService::_existingRedirectDestination()` makes a read-only call to Retour's own `getRedirectByRedirectSrcUrl($destPath, $siteId)` — if the entry's destination already has an outbound redirect of its own, both redirects are still created/kept, and the page gets a warning: `Retour already redirects /new → /theirs; legacy redirect /old → /new will chain — review in Retour.`

**`associatedElementId` is deliberately left at its default (0), never set to the entry's id.** Retour's own CP Redirects-list query (`TablesController::actionRedirectTableData()`) filters `associatedElementId = 0` — any non-zero value is treated as a "Short Link" and hidden from the Redirects list entirely. A redirect this pass creates needs to be visible and editable there, so `saveRedirect()`'s config array never includes the key.

**Dry-run.** No writes; each page that would get a redirect reports one `Would create redirect: /old → /new` line PER SOURCE VARIANT (so two lines for an ordinary path) in the same per-owner warnings map PASS 3 uses. The chain-warning check above still runs on a dry run (it's read-only), so the preview surfaces it too.

**Re-syncing a page that already has a (wrong) redirect.** `saveRedirect()` upserts on Retour's own (`redirectSrcUrlParsed`, `siteId`) key, so re-running a sync with the affected pages unlocked corrects an existing row in place — no manual cleanup of bad rows is needed beyond letting the next sync run.

**Test coverage.** The pure half — `RedirectService::legacyUrlToPath()`/`sourceVariants()`/`legacyUrlHadQuery()`/`entryUriToPath()` — is covered by `tests/run-transforms.php`, no Craft dependency. `sweep()` itself (the Retour/Entry calls, the actual `saveRedirect()`) has no automated coverage — same gap `LinkSweepService` has, for the same reason (no live Craft test harness in this repo).

## Find-or-create identity

Every write path needs to answer "does this page already have a Craft entry?" — that's `ImportService::findExistingEntry(array $pageData): ?Entry` (`src/services/ImportService.php:479`), the single resolver used by `importPage()` itself, `ImportPagesJob`'s lock check (shared by the CP Sync, CP upload, and `sync/run` pipeline sources, since all three route through it), and the CLI's own lock check. All agree, by construction, on which entry a page maps to.

Resolution order:

0. **`document.id` → `contentiq_entry_syncs.contentiq_page_id`.** Checked first. If a mapping row exists and its `element_id` still resolves to a live (possibly trashed-but-not-hard-deleted — `status(null)`) entry, that entry wins outright, no further lookup. This is the important one: it means a page renamed on either side (ContentiQ or Craft) still resolves to the same entry instead of creating a duplicate — the column was added specifically to fix that (`src/migrations/m260813_000000_add_page_id_to_entry_syncs.php`). A stale mapping (element hard-deleted) falls through to the steps below rather than failing.
1. **`document.content_type` set** → route via `getContentTypeRoute()`, then section + slug lookup in the routed section.
2. **`document.is_homepage`** → section-only lookup of the homepage Single (no slug involved — Singles have exactly one entry).
3. **Otherwise** → the configured pages section + slug.

An empty/whitespace slug never drives steps 1 or 3 (Craft treats a falsy `->slug()` filter as "no filter," which would match the section's first entry rather than "no match") — those steps return `null` instead. Step 0 and step 2 don't depend on slug, so they're unaffected.

`findExistingEntry()` applies no slug translation — `slugMap` (see [integration.md](integration.md)) is only an optional override for the sidebar widget's *outbound* API call (which otherwise resolves its own locator — stored ContentIQ id, then homepage `__home__`, then the Craft slug — see [cp-and-widget.md](cp-and-widget.md)), never this Craft-side lookup.

## Homepage specifics

A page with `document.is_homepage: true` resolves via step 2 above (the configured `homepageSection`/`homepageEntryType`, default `homepage`/`homepage`) instead of the ordinary pages Structure, and gets different treatment in a few places once resolved:

- **Title is never overwritten on an existing homepage entry** — `importPage()` guards the `$existing->title = $title` assignment with `if (!$isHomepage)` (`src/services/ImportService.php:361`). A brand-new homepage entry (the Single's very first save) does get the exported title, same as any other new entry.
- **No structure positioning.** Both `ImportController::_runBatch()` and `ImportPagesJob::_processPage()` explicitly skip the parent/root append step for homepage pages (`!$isHomepage` guards) — Singles have no parent to set.
- **Same `hero` ContentBlock field as ordinary pages** — `_buildHeroField()` doesn't distinguish homepage from pages architecturally; see [block-mapping.md](block-mapping.md#hero).

## Hierarchy — parent/child positioning for Structure pages

After a page (non-homepage, non-collection-child) is saved, `ImportPagesJob` (the CP Sync/upload/`sync/run` pipeline's shared batch job) repositions it in the section's Structure using `document.parent_slug` and `document.sort_order`, via one shared method: `ImportService::positionInStructure(Entry $entry, ?int $parentId, int $structureId, int $sortOrder, ?int $contentiqPageId, array &$warnings): void`.

**Parent resolution** happens in the caller, unchanged from before this method existed:

- No `parent_slug` → `$parentId = null` (root level).
- `parent_slug` present → resolved against the in-run `$slugToEntryId` map first (pages already processed earlier in this same batch), and if not found there, a live Craft query (`Entry::find()->section(...)->slug($parentSlug)`) — so a re-import correctly re-parents under a page that already exists in Craft even if the batch itself isn't depth-first ordered. Only when **neither** finds the parent does the caller fall back to `$parentId = null` (root), with a warning naming the missing slug. Nothing later retries this automatically — the next sync that successfully resolves the parent will reposition it.

Depth-first ordering in the export (parents before children) is what makes the in-run map hit on the first pass rather than falling through to the query — not a hard requirement for correctness, just for avoiding an extra DB lookup per child on a fresh import.

**Sibling positioning** is `positionInStructure()`'s own job. Every export `document` carries `sort_order` — an int, scoped per parent, ties broken by `document.id` — but a plain `append()`/`appendToRoot()` ignores it entirely and always lands the page LAST among its siblings. That's fine for a full, depth-first, single-pass import, but wrong the moment a sync is partial (a locked entry skipped, a deselected "New" row, a single-page widget sync): the next page written lands after siblings it should sort before. `positionInStructure()` fixes this by reading where the page actually belongs:

1. Loads the entry's current siblings under the resolved parent (root level when `$parentId` is null), in structure order, excluding the entry itself — section-scoped implicitly via `structureId` (`level(1)` at root, `descendantOf($parentId)->descendantDist(1)` under a parent).
2. Fetches those siblings' stored `(sort_order, contentiq_page_id)` from `contentiq_entry_syncs` in one query, keyed by element id.
3. `StructureOrder::insertBeforeId()` (`src/helpers/StructureOrder.php`, pure and Craft-free — see `tests/run-transforms.php`) finds the first sibling whose `(sortOrder, pageId)` sorts strictly after the target's own — comparison is `sortOrder` first, `pageId` breaking ties, matching ContentIQ's own ordering rule.
4. `moveBefore()`s the entry there when a sibling comes back, or falls back to the existing `append()`/`appendToRoot()` when nothing sorts after it (the page belongs at the end).

**A sibling with a stored `sort_order` of `null`** — a Craft-only entry never synced from ContentIQ, or a row that predates the `sort_order` column — is skipped by `insertBeforeId()` rather than treated as "sorts first." It keeps its existing place instead of being shoved to the front of its siblings on every sync.

**Persistence.** `sort_order` is written onto `contentiq_entry_syncs` wherever that table's row is already upserted for a page — `FinaliseRunJob`'s `lock` step and `CpController::actionWidgetSync()`'s single-page upsert — always, not guarded behind an emptiness check like `contentiq_page_id` is, because `0` is a legitimate first-sibling value. Because `CpController::actionRunImport()` (the JSON-upload path) now routes through the same pipeline as CP Sync, its pages get this same `contentiq_entry_syncs`/`sort_order` upsert too (the `lock` step is not skipped for `source=upload`, unlike `ack` — see "The job chain — phase by phase" above); before this pipeline existed, uploaded pages had no such upsert step at all and `sort_order` was never persisted for them.

**Existing sites** synced before this column existed have every entry's stored `sort_order` at `null` (skipped, not sorted first — see above) until each page goes through a real sync again. `php craft contentiq-importer/structure/reorder` (`src/console/controllers/StructureController.php`) is a one-time catch-up: it re-fetches the whole-project export and repositions every already-synced page using the same `positionInStructure()` logic, backfilling `sort_order` as it goes, without writing content, acknowledging pages, or touching locks. `--dry-run` reports what would move and writes nothing. Unlike the pipeline's own import path — which saves a page with an unresolvable `parent_slug` at root with a warning, correct for a page being written for the first time — the repair command SKIPs that page entirely instead: it already has a real position (and possibly a whole subtree beneath it), so silently relocating it to root would be destructive, not corrective.

**URI-timing trap.** `Structures::append()`/`appendToRoot()`/`moveBefore()` all trigger Craft's own `Entry::afterMoveInStructure()`, which regenerates the entry's URI — but via a QUEUED job (`updateElementSlugAndUri($this, true, true, true)`), not an inline write. Since a pipeline run is itself a queue job, that queued write only lands after the current run finishes. `positionInStructure()` calls `ImportService::refreshUri($entry)` right after the move, inside its own `try`, to force the URI into the DB before anything else in this run reads it. See "`saveElement($entry, false)` and the manual URI refresh it necessitates" below for the full explanation, and "Pass 4 — legacy-URL redirects" for why this mattered in production.

**The sidebar widget** (`CpController::actionWidgetSync()`) never repositions its entry at all — it only calls `importPage()` and writes its `contentiq_entry_syncs` row (including `sort_order`, so the entry stays a correctly-ordered sibling for the *next* batch sync). A single-page widget sync has no batch context to resolve a parent against, so it was never wired into structure positioning, before or after this change.

## Why the owner entry is resolved before the Matrix is built

In `importPage()`, `findExistingEntry()` runs (step 6, `src/services/ImportService.php:171`) *before* `MatrixBuilder::build()` is called (step 7, `:231`) — that ordering was deliberately moved up from a later point in the pipeline specifically to support `preserveBlockIdentity` (off by default; see [integration.md](integration.md#config-surface) and [block-mapping.md](block-mapping.md#diff-aware-matrix-writes-preserveblockidentity) for the full mechanic and its live-validation checklist). When it's on and the owner entry already exists, its current top-level block map (`contentiq_block_syncs`: payload block id → nested Matrix element id) is loaded (`_loadBlockSyncMap()`) and handed into `MatrixBuilder::build()` so unchanged top-level blocks can be emitted with their real element id instead of a fresh `'new*'` key — letting Craft update them in place rather than delete-and-recreate, which is what preserves editor provisional drafts attached to those blocks across syncs. After a successful save, `_recordBlockSyncMap()` writes the map for the *next* sync to consume (`src/services/ImportService.php:381-383` for the existing-entry branch, `:423-425` for the newly-created-entry branch) — bookkeeping only, wrapped in its own try/catch so a failure there can never fail the page save itself. When the flag is off (the default), `$existingBlockMap` is always empty and every top-level block gets a `'new*'` key exactly as it did before this feature existed — byte-identical behaviour.

## The no-drafts rule

The importer saves directly to the canonical entry — `Craft::$app->getElements()->saveElement($entry, false)` — never through `getDrafts()->createDraft()`. This was a deliberate correction: an earlier version used drafts, which wrote images into the database successfully but left them invisible in the CP, because the CP entry-edit screen renders the canonical entry's content, not a draft's. That cost real debugging time before the pattern was fixed, and it's now settled — every write path in `ImportService` uses this same call, for both existing-entry updates and new-entry creates.

## `saveElement($entry, false)` and the manual URI refresh it necessitates

The `false` argument skips Craft's element validation. This is necessary because nested nothing-changed Matrix blocks can trip `MatrixBlockAnchorField` uniqueness validation that has nothing to do with whether the actual content is valid — see [block-mapping.md](block-mapping.md#setting-field-values--data-shapes-and-exploring-a-target-project) for the underlying Matrix-write data shapes and key rules this interacts with.

The cost of skipping validation: **URI generation is a validation-time concern in Craft** (`ElementUriValidator`), so a validation-skipped save leaves `uri = null` — the entry has no front-end URL and no "view" globe icon in the CP, even though the save otherwise succeeded.

- **Pages** (Structure section) get repositioned via `Structures::append()`/`appendToRoot()`/`moveBefore()` inside `positionInStructure()`, and that call's `afterMoveInStructure()` hook (`vendor/craftcms/cms/src/elements/Entry.php`) does regenerate the URI — but via `updateElementSlugAndUri($this, true, true, true)`, whose trailing `true` QUEUES the write as a separate `UpdateElementSlugsAndUris` job rather than performing it inline. **Trap:** because a pipeline run is itself a queue job, that queued write lands strictly after the current run finishes — anything later in the SAME run that reads `$entry->uri` sees it empty (PASS 4's legacy-redirect sweep hit this in production, building every redirect's destination as `/`). `positionInStructure()` itself calls `ImportService::refreshUri($entry)` (`src/services/ImportService.php:911`) immediately after the move, inside the same `try`, to force the write inline before anything downstream needs `uri`.
- **Collection children** (channel sections — blog posts, case studies, team members) have no structure step at all, so nothing does this for them implicitly. `_importCollectionChild()` (`src/services/ImportService.php:1063`) calls the private `_refreshUri()` (`src/services/ImportService.php:1319`) explicitly after every save, which invokes `Craft::$app->getElements()->updateElementSlugAndUri($entry, true, false)` directly (not queued) — regenerating slug + URI without re-running full element validation. This is a no-op (leaves `uri = null`) if the section has no URL format at all.
- **Any other same-run read of `$entry->uri` after a structure move** — not just the two paths above — must force a refresh first. See "Pass 4 — legacy-URL redirects" below for the belt-and-braces check `RedirectService::sweep()` also does, in case a caller upstream ever skips the inline refresh.

## Native attribute writes: title and postDate

`title` and `postDate` are Craft native entry attributes, set directly on `$existing`/`$entry` before `setFieldValues()` — not part of the field-values array `_filterToValidFields()` below screens. `title` is unconditional except for the homepage guard above. `postDate` is written from `document.original_publication_date` — gated on the `postDate.pages`/`postDate.collections` config toggle (default `true` for both; homepage counts as `pages`) — via `ImportService::_applyPostDate()`, called on both the create and update branch of `importPage()` and `_importCollectionChild()`. It overwrites unconditionally when a value is set (whole-page replace, same as every other synced field); a false toggle or a null/empty date leaves it completely untouched (a brand-new entry keeps Craft's own "now" stamp, an existing entry keeps whatever it had); an unparseable date string adds a page warning instead of guessing. Parsed with `DateTimeHelper::toDateTime($raw, true)` so a bare `YYYY-MM-DD` resolves to midnight in Craft's own system timezone, not UTC. See [integration.md](integration.md#config-surface).

## Field-layout filtering before `setFieldValues()`

Every field-values array built by the pipeline (Matrix data, hero fields, SEO fields, card fields, collection-child content fields) is passed through `_filterToValidFields()` (`src/services/ImportService.php:1228`) before being handed to `setFieldValues()`. This intersects the built values against the target entry type's actual field layout and drops anything not present. Skipping this throws `yii\base\UnknownPropertyException` ("Setting unknown property: CustomFieldBehavior::handleName") in Craft 5 the moment an unrecognised handle is set — so this filtering isn't optional defensive code, it's required for the importer to tolerate a Craft Starter fork whose field layout doesn't (yet, or ever) match every handle the mapping config expects. Filtered-out fields aren't silently lost from the report either — several of the guard checks upstream (e.g. the text-block first-column probe, the hero-shape probe) look at the field layout *before* building values specifically so they can route around a missing field rather than relying on this filter to catch it after the fact.

## Content-type routing for collection children

A page whose `document.content_type` is set (blog posts, case studies, team members, blog categories) is a **collection child**, not an ordinary Structure page, and is routed through a separate path, `_importCollectionChild()` (`src/services/ImportService.php:839`), from the very top of `importPage()` (`src/services/ImportService.php:124-127`) — before section/entry-type resolution, before the hero/CTA extraction, before anything the ordinary page path does.

**The wire contract: `content` and `blocks[]` can now travel together.** Historically (and still, for a collection child with no ranges marked up at all) a collection child carried a raw `content` ProseMirror document (not a `blocks` array) that got serialised whole to HTML and written into one configured `contentField`, with no `blocks` key present. ContentiQ is transitioning collection children onto the same `blocks[]` shape ordinary pages use: once ranges are marked up, the export carries `blocks[]` plus an **optional** `content` key holding the page's explicitly-marked **Body Text** sections — a MANUAL markup block the editor applies deliberately, merged in page order — present only when the editor marked at least one Body Text range, and omitted entirely when they marked none. Regular (non-collection) pages are unaffected either way; they never carry a `content` key. The importer already handles all of this: when `blocks[]` is present and non-empty, the same Matrix/hero/CTA machinery the page path uses runs via `_buildBlockFieldValues()`, routed to a Matrix field (`blocksField` from the content-type mapping if set, otherwise the ordinary `matrixField`). `headingField` — when configured — is always explicitly cleared to `''` once blocks own the page; `NodesRenderer::extractHeading()` never runs on this path, since blocks own the heading, not the Body Text. `contentField` depends on whether the editor marked any Body Text: when the (optional) `content` key is present and non-empty, that Body Text is rendered wholesale (`NodesRenderer::renderDocument()`, unstripped — no heading extraction) into `contentField`; when `content` is empty or absent — including against an older ContentiQ deployment that still only ever sends `blocks[]` with no `content` key at all — `contentField` is explicitly cleared to `''`, exactly as before this Body Text contract existed, rather than left stale from a prior content-only sync (`_buildCollectionChildContentFields()`, `src/services/ImportService.php:2710`). The first time an unlocked sync is about to clear (or replace with Body Text content) a previously non-empty `contentField`/`headingField`, or replace a previously non-empty Matrix, a warning is added to the result — its wording adapts to which of the two happened (`_buildBlockOwnershipWarnings()`) — this fires identically in the CP dry-run preview and the real sync, so an editor sees it coming before it happens, though nothing blocks the write itself (the lock is the only thing that can prevent it). `horizontalRule` nodes never arrive in a rendered `contentField` either way — they're a ContentiQ layout aide, stripped at export, and `NodesRenderer::renderDocument()` skips them defensively regardless (belt-and-braces for older app payloads and legacy full-content syncs).

**`headingField` H1 lifting** (content-only path): when a content-type mapping configures a `headingField` and the child is on the `content`-document path (not `blocks[]`), the importer extracts the first level-1 heading out of the document via `NodesRenderer::extractHeading()` and writes its plain text into `headingField`, removing it from the body so the H1 doesn't render twice — once as the field, once inline in the content. `blog_categories` and `team` in the shipped defaults have no `headingField` because their templates don't render one from a separate field.

**Routing is a three-layer merge**, `_getContentTypesMap()` (`src/services/ImportService.php:769`): `src/config/defaults.php`'s `content_types` array ← the CP Mappings screen's saved settings (`Settings::$collectionMappings`, project config) ← `config/contentiq.php`'s own `content_types` key. Per-slug `array_replace` at each layer — the config file always wins for a given slug and is meant as the dev escape hatch; the CP screen (`ContentiQ → Mappings`) is the editor-facing way to map a new collection without a deploy. Settings rows with no `section` are dropped before merging, so an empty CP mapping table doesn't disturb anything.

**An unmapped `content_type`** (no route found at any layer) is a non-fatal skip: `_importCollectionChild()` sets `skipped = true`, `success = true`, and a warning naming the type and pointing at the Mappings screen (`src/services/ImportService.php:848-856`) — the whole run isn't failed by one unrecognised collection.

**No Craft parent.** Collection children never get structure positioning — `ImportPagesJob`'s hierarchy step explicitly excludes them (`$contentType === null && ...` guards the whole block, `src/jobs/ImportPagesJob.php`) and `document.parent_slug` is simply never read for them. This is intentional, not a gap: a collection child's real "parent" is its collection listing page, which is excluded from export server-side and has nothing to attach a Craft Structure parent to.

## CTA source routing

Every `call_to_action` block carries `fields.source` (`'page'` or `'global'`, absent ⇒ `'global'`), and `ImportService::_resolveCtaBlocks()` routes each one accordingly — shared by both places blocks are turned into field values, `importPage()`'s own body (ordinary pages/homepage) and `_buildBlockFieldValues()` (collection children carrying `blocks[]`, see above), so every entry point routes CTA blocks identically since all of them funnel through `importPage()` (see "Four entry points, one pipeline method"). `'page'` is the pre-existing behaviour, untouched: an inline `callToAction` Matrix block relating to a per-page entry tracked in `contentiq_cta_syncs`. `'global'` drops the placeholder from the page entirely and creates/updates a single SHARED `callToActionEntry` related on the `globalContent` global set — gated on the same globals-consent lock `GlobalsImportService`/`FinaliseRunJob`'s `globals` step use (see [globals.md](globals.md)). Once every block on the page is classified, `_resolveCtaBlocks()` also resolves a single page-level decision for the `callToAction.showGlobalCallToAction` lightswitch (read-modify-write — every sibling field, notably `callToActionLayout`, is left untouched): **ON** when ≥1 block routed `'global'` this run, **OFF** when the page carried ≥1 `'page'`-source block and none `'global'`, or left **untouched** when there were no CTA blocks at all. Full mechanics, including the `UnknownPropertyException` field-layout guard (whose warning is asymmetric — silent on a missing field when the decision is OFF, since collection children routinely have no footer field to disable), why the global entry isn't tracked in `contentiq_cta_syncs`, and why both routing notes land in a dedicated `routingNotes` result key rather than `blockNotes` or `warnings` (`blockNotes` is reserved for ContentIQ's own payload-authored `block.notes`, which persists into `contentiq_entry_syncs.notes` — routing messages must never reach that column; `warnings` is reserved for actionable problems and drives run/page status, and routing itself is expected behaviour, not one), live in [block-mapping.md](block-mapping.md#source-routing-fieldssource-page--global) — this pipeline doc only notes where it sits: routing happens as part of step 10 below, before step 11's field-values assembly, so a `'global'`-routed block's `callToAction` write lands in the SAME `setFieldValues()`/`saveElement()` call as the rest of the page — no second save.

## Per-page error isolation

`importPage()` wraps its entire body in one `try { ... } catch (Throwable $e)` (`src/services/ImportService.php:83`, `:429`) that converts any exception — a save failure, a missing section, a malformed block, an unexpected null somewhere deep in a handler — into the same fatal result shape (`success: false`, `error: ...`) rather than letting it propagate. That's what makes a batch sync resilient to one bad page: `ImportPagesJob::processItem()` calls `importPage()` per row and simply records whatever comes back, success or failure, then moves to the next row — even a `\Throwable` that gets past `importPage()`'s own catch (or is thrown from code *around* the call, like the structure-positioning step) is caught by `processItem()`'s own wrapping try/catch and recorded as `status=failed` on that one row, never aborting the batch. Only an exception thrown from `beforeBatch()`/`afterBatch()`/`after()` — outside any per-row try — reaches the job's own outer catch and fails the whole run.

## Result shape and dry-run

Every call to `importPage()` returns the same associative array shape, starting from `_emptyResult()` (`src/services/ImportService.php:1052`) and either merged with real data on success or marked fatal by `_fatal()` (`src/services/ImportService.php:1078`, which also logs the message via `Craft::error()` before returning). Read `_emptyResult()` directly for the exhaustive key list rather than copying it here; the keys worth knowing about because callers actively branch on them are `success`, `entryId`, `entryFound` (create vs update), `warnings` (non-fatal, accumulated throughout the run), `error` (set only on a fatal result), `skipped` (a non-fatal skip — e.g. an unmapped `content_type`), and `cardRefs` (pass-2 deferred work, consumed by the caller, not part of the "public" result a report screen would render).

`dryRun` is honoured inside `importPage()` itself — it runs every resolution step (config, matrix build, SEO, hero, card fields) and returns before step 10 (CTA entry creation/routing, see "CTA source routing" above) and the actual save (`src/services/ImportService.php:263-267`), so a dry run still reports accurate block/image/warning counts without writing anything. Not every entry point exposes it, though:

- **CLI** — `--dry-run` / `-n` flag, passed straight through.
- **CP upload** — `actionPreview()` (`src/controllers/CpController.php:281`) always dry-runs every page before showing the preview screen, regardless of any flag; the real write only happens after the user confirms and the upload run is staged onto the pipeline (`actionRunImport()` → `StageRunJob`, always `dryRun: false`) for real.
- **CP Sync and `sync/run` (the pipeline's other two `source`s)** — never dry-run; a queued/staged run is already a confirmed action. (The Sync screen's *tree preview*, shown before the user clicks Sync, is a separate, lighter-weight read — see [integration.md](integration.md) — not a dry run of `importPage()` itself.) `actionPreview()` (dry run) stays synchronous, outside the batched pipeline — see "The job chain — phase by phase" above.
- **Sidebar widget** — never dry-runs; clicking Sync in the sidebar is itself the confirmation.

## Lock semantics

Lock state lives entirely in `contentiq_entry_syncs.locked`, per Craft entry (`element_id`). A **missing row** is treated as locked everywhere it's checked — the safe default, so a hand-built entry that happens to collide with a synced slug/section (no sync row yet) is never silently overwritten just because nothing has locked it explicitly.

- **Batch sync (`ImportPagesJob`, shared by CP Sync, CP upload, and `sync/run`)** — locked entries are skipped in the `importing` phase, logged as "Skipped — entry is locked" in the report, and left completely untouched (their existing `locked`/`synced_at`/`notes` row is not rewritten, so the audit trail correctly shows it was skipped rather than looking like a fresh sync happened). Every successfully-synced entry is auto-relocked at the end of the run by `FinaliseRunJob`'s `lock` step (see "The job chain — phase by phase" above) — the Sync screen's per-entry checkboxes are how a human unlocks specific entries for the *next* run, not a persistent state. Unlocking a never-synced entry (no row yet) is handled by `_applyLockState()`'s upsert (see `StageRunJob`'s `staging` step above) — without it, ticking "unlock" for such an entry silently no-ops and the entry is skipped as locked anyway. A CP-uploaded file has no unlock-selection UI of its own (`unlockIds` is always `null` for `source=upload`), so every entry it touches is either already-unlocked or locked — a locked entry cannot be overwritten by re-uploading a file, full stop.
- **Per-entry, via the sidebar widget** — a CSS-only lightswitch (deliberately not Craft's native lightswitch component, which needs DOM-ready init that doesn't fire reliably for HTML injected into the sidebar after page load) toggles the same `locked` column immediately via `contentiq-importer/cp/toggle-lock`, and disables the widget's own Sync button client-side when on. `CpController::actionWidgetSync()` re-checks the lock server-side regardless (`src/controllers/CpController.php:1101-1113`) — the disabled button is advisory only, not the actual enforcement.
- **CLI** (`php craft contentiq-importer/import`, not `sync/run`) — enforces the same lock check unless `--force` is passed (`ImportController::_runSinglePage()`, `src/console/controllers/ImportController.php:439`); this is the standalone CLI pipeline, not routed through `ImportPagesJob`.
